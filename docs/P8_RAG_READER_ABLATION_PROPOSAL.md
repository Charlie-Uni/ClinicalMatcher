# P8 提案：检索输入 × 8B 读取器消融（RAG reader ablation）

状态：**owner 已确认**（2026-09-18，原话「同意修改」，R1–R6 全部接受）。
本提案只新增实验，不改动任何已封存的契约、切块、索引或现任候选。
实现：`clinical_matcher.p8_reader`（运行器 1.0.0，四臂共用 v1 提示/schema/解码，
B/C 读取冻结的 P3 RRF 检索文档并 pin，契约记录运行时身份），CLI
`prepare-reader / pilot-reader / run-reader`；合成测试 `tests/test_p8_reader.py`。

## 1. 动机与证据边界

- P3 的三条检索臂（患者内 BM25、MedCPT 稠密、RRF 融合，各取 top-3）
  的下游读取器是确定性规则抽取器（typed EM 0.316–0.319，规则读整份病历
  0.328）。**检索从未接到 8B 模型上**；"检索对 8B 影响大"目前是假设。
- 现任 `long_context.A1`（0.629）来自 8B 读整份病历（中位 12k 字符）。
  8B 模型在长输入上可能"迷失在中间"，聚焦输入可能更好，也可能更差。
- 无独立证据相关性 gold；本提案只以下游 typed exact match（validation，
  raw 视图，development diagnostic）为信号，不宣称检索相关性。

## 2. 实验臂（全部使用 v1 系统提示原文与 v1 输出 schema，8B，同一运行时）

| 臂 | 输入 | 请求数/患者 | 目的 |
|---|---|---|---|
| A | 整份病历，23 题合批（v1 重放） | 1 | 同运行时基线；跨硬件差异已证实，缺它则任何对比无效 |
| B-m | 23 题合批，患者级只保留 m 个块：按各题 RRF 融合分数对块取最大值排序，m ∈ {3, 5} | 1 | 检索裁剪上下文，其余与 A 完全相同 |
| C | 逐题请求，每题 RRF top-3 块 | 23 | 你原意的"每题检索"RAG |
| D | 逐题请求，整份病历（C 的对照） | 23 | 把"逐题请求本身"与"检索"分离 |

固定网格：m ∈ {3, 5}，per-question k = 3（与 P3 一致）。不在网格外调参。

## 3. 判定规则（预声明）

- 主指标：validation typed exact match（raw）；辅助：gold-absent 布尔召回、
  数值 tolerance accuracy、请求接受率。
- 检索臂**只有同时满足**才保留：typed EM 高于同运行时的 A，且 gold-absent
  布尔召回不低于 A。否则记为负向消融。
- 若 D 明显低于 A 而 C 接近 D，则逐题请求本身是问题，与检索无关。
- 所有数字标注 development diagnostic；选择仅在 validation；holdout 不动。

## 4. 我将如何修改 RAG（需你逐条确认）

R1 **不重新切块**。冻结的 2,000 字符块与 evidence_id 保持不变；重切块等于
   新的切块契约版本，只在本提案第一阶段证明"检索有益"后再议。
R2 **修稠密编码截断**（第二阶段，仅当第一阶段检索臂不劣于 A）：MedCPT
   文章编码器截断 512 token，2,000 字符临床文本常超过该长度，块尾未被
   编码。修法：每块按 ≤512 token 分窗编码、取最大相似度作为该块分数；
   块边界与 id 不变；作为稠密契约 1.1.0 单独成臂对比。
R3 **查询构造**（第二阶段）：第一阶段沿用 P3 冻结查询（问题原文）；第二
   阶段允许把规则集中该题的关键词表拼入查询（确定性、不用模型、不用
   gold），作为单独臂。
R4 **不加重排器、不用模型生成查询、不训练检索器**；RRF 常数 60 不变。
R5 **每臂一份封存契约**，记录运行时身份（引擎版本、硬件）、输入策略、
   网格取值；输出只打印聚合数。
R6 **实现方式**：新增运行器模块（复用 v1 的消息构造与 schema、E1 的运行时
   探测/重 pin、预算与试验闸门、P3 的 BM25/稠密/RRF 计算函数）；不改 v1
   运行器，不改 P3 检索模块。

## 5. 成本

实现约 2–3 小时（含测试与 CI）。GPU 上：A 与 B 各 15 请求（每臂约 2–3
分钟），C 与 D 各 345 请求（每臂约 10–15 分钟）；四臂加网格合计 1 小时内。

## 6. 与 E2 的顺序

本提案在 E2 之前执行：若某检索臂被保留，E2 的每个模型按同样四臂中被保留
的输入策略运行；否则 E2 只跑 A。
